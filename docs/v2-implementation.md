# Первый этап реализации v2: 19 сентября 2026

Это исторический отчёт первого этапа, включая тогдашний API, 162 теста и замеры. Актуальное состояние описано в [отчёте следующего этапа](v2-polish.md).

Работа выполнена в ветке `codex/domwires-v2-scopes`, исходная точка — `08c80f955e63d652f0ab568ef0a38be760d8fd3f`. Исходный аудит находится в `analysis/review-2026-09-19`; его результаты относятся к состоянию до изменений.

Идея DomWires сохранена: намерение медиатора → сообщение → контекст и guards → команда → модель → уведомление → медиатор. Суффикс `Immutable` сохранён и определён как интерфейс живой модели без методов изменения.

## Что перенесено из Devkit

| Возможность | Реализация в ядре |
| --- | --- |
| Регистрация одной модели под mutable/immutable-контрактами | `registerModel()`, отдельные typed tokens |
| Разделение зависимостей команд и читателей | Области для command/model/mediator/adapter, `provide()`, `createMediator()`, `createAdapter()` |
| Дочерние контексты | `createContext()/addContext()`, явные импорты зависимостей и предикаты маршрутизации |
| Управление жизненным циклом | `own/defer/start/close`, `ResourceScope`, disposable subscriptions |
| Реестр реализаций для конфигурации | `factory.registry`, без поиска классов в `globalThis` |

Обязательный базовый Service не вводился. Команда может быть асинхронной, адаптер отвечает за внешнюю систему, контекст владеет соединением. HTTP, MongoDB, Socket.IO, email/auth и UI-специфика остались вне ядра.

CLI-каталог, snapshots и генерация моделей не перенесены автоматически: это отдельные инструменты. В частности, старый SnapshotModel с записью в подчёркнутые поля через reflection не стал контрактом новой модели.

## Основные исправления

- У каждой команды своя область данных; глобальный LazyRegistry удалён.
- Native async `execute()` действительно ожидается. По умолчанию создаётся новый экземпляр команды; явный singleton защищён от перекрывающихся запусков.
- `once` удаляет конкретную регистрацию до вызова пользовательского кода; mapping handles можно освобождать отдельно.
- Очередь ожидания хранит активную работу, учитывает прямые команды и дочерние контексты, не теряет медленные операции после ошибки.
- Именованные и обычные дети имеют один порядок доставки; исправлены удаление, перепривязка, дубликаты ID и циклы.
- Listener iteration и метаданные доставки устойчивы к вложенным сообщениям и изменению регистраций.
- Добавлены typed tokens, типизированные `mapCommand()/execute()`, constructor/provider DI, обнаружение циклов зависимостей.
- Исправлены named config instances и создание при наличии value binding; пулы проверяют размеры и освобождают принадлежащие им объекты.
- Добавлены проверки распространяемого tarball, запуск CI на pull_request, `npm ci`, исходники в пакете и sourcesContent в JS maps.

Динамические `map()/executeCommand()` и строковые идентификаторы остаются низкоуровневыми средствами конфигурации. Для строгой проверки входных данных используются typed tokens и `mapCommand()/execute()`. Legacy property decorators сами по себе не проверяют соответствие типа поля токену; этот предел явно описан.

## Проверка

- 162 runtime-тестов проходят, включая сквозные сценарии из `examples/scoped/RequestContext.ts`.
- Негативные type assertions проходят: ошибки payload/listener/command/token отвергаются компилятором.
- Typecheck и lint проходят; lint без предупреждений.
- Сборка библиотеки, frontend-примера, VM smoke и browser test bundle проверяются стандартными командами.
- Упакованный tarball установлен в отдельный consumer: проверены CJS, ESM, declarations и minified browser bundle.
- В настоящем браузере проверено: 0 → клик → 1 → Remount → 0 → клик → 1; ошибок в консоли нет.

Исходные probes R01–R21 превратились в сценарии обычного набора тестов. Некоторые исходные диагностические probes намеренно зависают на исправленном поведении, поэтому старый standalone-скрипт предназначен только для исходной ревизии.

## Измерение горячего пути

На Node 24.18.0, 10 000 сообщений, медиана пяти запусков:

| Сценарий | До изменений | После изменений |
| --- | ---: | ---: |
| Без command mapping | 10,03 мс | 6,76 мс |
| Пустая синхронная transient-команда | 61,79 мс | 42,00 мс |
| Завершённые сообщения в pending после прохода | 10 000 | 0 |

Это microbenchmark на одной машине, не прогноз FPS или серверной пропускной способности. В обоих вариантах команды явно transient, то есть сравнение не подменено разным временем жизни экземпляров. Сохранены все samples и heap deltas в `analysis/review-2026-09-19/benchmark-before.txt` и `benchmark-after.txt`. Удалены лишние promise bookkeeping и контейнер для старого lazy-реестра; кэшируются планы property injection.

## Дальнейшие отдельные улучшения

На следующем этапе реализованы единый API команд, parallel/serial/latest/drop, trace hooks, игровой пример и автоматические браузерные проверки в CI. Snapshots/codegen, CLI-каталог и отдельная ESM-сборка остаются самостоятельными задачами.

Отмена кооперативная: signal передаётся адаптеру, а `execution.commit()` защищает изменение после await. Фреймворк не может принудительно остановить произвольный JavaScript; игнорирующая отмену незавершающаяся команда задержит `close()`.
