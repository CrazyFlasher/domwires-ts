# Полировка v2: API, команды, игровой пример и проверки

Работа продолжает первый этап в ветке `codex/domwires-v2-scopes`. Здесь описано текущее состояние. Отчёт первого этапа и его замеры сохранены в [v2-implementation.md](v2-implementation.md).

## Выполненный план

1. **Единый API команд.** `map(message, Command, options)` и `execute(Command, input, options)`. Удалены `mapCommand`, `executeCommand`, `tryToExecuteCommand` и позиционные флаги регистрации. Batch-регистрация проверяет типы входных данных. Для внутренней доставки уже созданного сообщения есть `route(message)`.
2. **Игровой пример.** `examples/game`: корневой контекст, сменяемая сцена и отдельный HUD; tick; пул из 12 снарядов; асинхронный адаптер загрузки; переключение сцены во время загрузки; отображение trace.
3. **Политики команд.** `parallel`, `serial`, `latest`, `drop` для каждой отдельной регистрации. Отмена отслеживается отдельно от ошибок.
4. **Трассировка.** Сообщение, guards, очередь/пропуск, начало и результат команды, длительность, идентификаторы для связи событий. Накопление истории оставлено наблюдателю; пример хранит последние 50 строк.
5. **Автоматическая проверка.** Chromium через Playwright, отдельная задача CI с отчётом, длительные проверки жизненного цикла и памяти.

Концепция Domwires сохранена: медиатор отправляет намерение, контекст выбирает команду, команда меняет модель, уведомление модели приходит читателю через контекст. `Immutable` остаётся интерфейсом живой модели без методов изменения. Адаптер — обычный объект, асинхронный сценарий находится в команде.

## Контракты, на которые можно опираться

- `lifetime: "execution"` создаёт экземпляр на запуск. `"context"` хранит экземпляр по классу внутри mapper до его закрытия. Одновременное использование сохранённого экземпляра отвергается.
- Очередь принадлежит mapping, а не классу команды. Даже одинаковые классы в разных mapping имеют разные очереди. Поэтому разные serial mapping всё ещё могут конкурировать за один context-lifetime экземпляр.
- `serial` выполняет FIFO, включая продолжение очереди после ошибки. Guards проверяются непосредственно перед запуском.
- `latest` отменяет предыдущие активные вызовы и начинает новый. Для него обязателен execution lifetime. Отмена кооперативная: адаптер получает signal, а `execution.commit()` защищает позднюю запись.
- `drop` пропускает занятый mapping. Пропуск не активирует `stopOnExecute`.
- Удаление mapping отменяет его активные и ожидающие вызовы. Автоматическое потребление `once` оставляет зарезервированный вызов работать.
- Отмена останавливает оставшуюся цепочку текущего сообщения. Независимые запросы продолжаются.
- Promise отменённого вызова отклоняется с `CommandCancelledError`; ожидаемая отмена не делает `settle()/close()` ошибочными. Реальные ошибки команды и cleanup не скрываются.
- Синхронные и асинхронные ошибки trace callback изолированы и учитываются в `traceErrorCount`. Асинхронный наблюдатель не задерживает команду и не входит в `settle()`.
- Mapper по умолчанию не хранит trace, payload или завершённые успешные задачи. Сбор ошибок до settle ограничен.
- Настройки по умолчанию: `CommandMapperConfig.defaultLifetime/defaultDataMode`; переопределения доступны в options. Объектные данные по умолчанию объединяются неглубоко, mapping data имеет приоритет. Режим `fallback` использует mapping data только при undefined message data.

Примеры:

```ts
context.map(LOAD_LEVEL, LoadLevel, {concurrency: "latest"});
context.map(SAVE_GAME, SaveGame, {concurrency: "serial", guards: [CanSave]});
context.map(SUBMIT, Submit, {concurrency: "drop", once: true});
await context.execute(Refresh, input, {signal: controller.signal});
context.trace = event => console.log(event);
```

## Дополнительные найденные и исправленные случаи

- Повторный запрос из обработчика abort не позволяет более старому latest-запросу вытеснить новый.
- Нельзя начать новую команду из обработчика отмены во время dispose mapper.
- Закрытие контекста из listener или команды прекращает дальнейшую обработку его сообщений.
- Ошибка property injection или post-construct после успешного конструктора вызывает cleanup частично созданного объекта.
- Неудачное присоединение нового child context или mediator освобождает этот объект.
- Ошибка асинхронного старта закрывает контекст и его компоненты.
- Optional property injection у сохраняемой команды возвращает исходное значение поля, когда в следующем запуске binding отсутствует; предыдущий payload не протекает в новый вызов.
- Ошибка getter входных данных и ошибка cleanup проходят через общий путь завершения команды.

## Проверка 19 сентября 2026

Локально: Windows, Node 24.18.0, TypeScript 7.0.2, Playwright 1.63.0, Chromium Headless Shell 153.0.8010.12.

- **192 runtime-теста** проходят.
- Негативные проверки типов проходят: payload, listener, direct input, batch mapping, options и удалённые aliases.
- Typecheck исходников, примеров и тестов; lint без предупреждений; сборка библиотеки проходят.
- Consumer из настоящего tarball: CJS, ESM import, declarations и minified browser bundle проходят. Это проверка ESM-потребителя, не отдельная ESM-сборка библиотеки.
- **3 браузерных сценария** проходят: 25 remount счётчика; игровой маршрут pool/tick/latest/scene/HUD/trace; 100 смен сцен и 100 полных перезапусков.
- **2800 жизненных циклов игры** проходят. После каждого — ноль активных загрузок, адаптеров, тиковых таймеров и объектов пула; внешняя подписка удалена; pendingCount равен нулю.

После прогрева Node retained heap вырос на 303 592 байта между 800-м и 2800-м циклом. Браузерная проверка после прогрева:

| Метрика | До | После 100 смен сцен и 100 перезапусков |
| --- | ---: | ---: |
| Documents | 1 | 1 |
| DOM nodes | 103 | 104 |
| Event listeners | 26 | 26 |
| JS heap | 2 130 676 B | 2 807 804 B |

Это проверка конкретной нагрузки и границ роста, не доказательство отсутствия любых утечек. GC, JIT и браузерные кэши влияют на heap. Stress-тест допускает 4 MiB роста после прогрева; браузерный — 2 MiB, дополнительно проверяя число документов, узлов и обработчиков.

Workflow добавлен для GitHub Actions; удалённый запуск CI в этой сессии не выполнялся. Node-матрица остаётся 20/22/24, browser job использует Node 24 и устанавливает Chromium. Отчёт и артефакты браузера загружаются даже при ошибке.

Браузер настроен по официальным механизмам Playwright: [webServer](https://playwright.dev/docs/test-webserver), [установка браузеров](https://playwright.dev/docs/browsers), [CI](https://playwright.dev/docs/ci). В Windows-песочнице ограничение на завершение дочернего процесса мешало остановке тестового сервера; полный прогон с разрешённым управлением дочерними процессами завершается штатно за ~19 секунд.

## Стоимость новых возможностей

Медиана пяти проходов по 10 000 сообщений, trace отключён:

| Сценарий | Первый этап | Текущий этап |
| --- | ---: | ---: |
| Без mapping | 6,76 мс | 6,22 мс |
| Пустая синхронная execution-команда | 42,00 мс | 59,19 мс |
| Завершённая работа в pending | 0 | 0 |

Отдельный сигнал отмены, учёт активных вызовов и scheduler добавили стоимость пустой команде: около 1,72 мкс на запуск в этом измерении. Это осознанная цена нового контракта, а не ускорение. Замер не предсказывает FPS реальной игры.

Samples сохранены в `analysis/review-2026-09-19/stage2-benchmark.json`, `stage2-stress.json`, `stage2-browser-metrics.json`.

## Как запустить

```sh
npm ci
npm run typecheck
npm test
npm run lint
npm run build
npm run test:consumer
npm run test:stress
npm run browser:install
npm run test:browser
npm run example
```

В примере перейти по ссылке **Open the scene lab**. Установленный браузер хранится в игнорируемом `.browser-cache`; `PLAYWRIGHT_BROWSERS_PATH` позволяет задать другой путь. Для Linux CI используется `npm run browser:install -- --with-deps`.

Snapshots/codegen, CLI-каталог, отдельная ESM-сборка и полноценный визуальный debugger остаются отдельными решениями; текущий план завершён без их добавления.
